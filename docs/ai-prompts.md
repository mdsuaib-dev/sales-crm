## 7. Authentication Debugging

### Problem

The frontend initially showed:

``` text
401 Unauthorized
Invalid or expired token
```

for protected endpoints.

### Investigation

The browser contained a JWT, but the backend rejected the stored token.

The login implementation signs tokens with:

``` ts
process.env.JWT_SECRET!
```

and the authentication middleware verifies with the same environment
variable.

### Correction

The stale browser token was cleared and a fresh login token was
generated.

The protected API request subsequently returned:

``` text
200
```

### Lesson

Before changing authentication code, verify:

1.  Token exists.
2.  Authorization header is present.
3.  Token was generated by the currently running backend.
4.  Signing and verification use the same secret.

## 8. JSX Debugging --- Bad AI Output and Correction

### Bad output

During an earlier JSX debugging session, an AI suggestion incorrectly
proposed removing a closing `</div>` around the Deals section.

### Why it was wrong

Inspection of the actual JSX structure showed that the problem was a
missing closing container, not an extra one.

### Correction

The incorrect suggestion was rejected. The correct structural fix was to
add the missing closing `</div>` for the Deals panel before the Users
section.

### Engineering lesson

AI-generated JSX fixes must be checked against the complete
DOM/component structure. A local-looking correction can create a larger
structural problem elsewhere in a large component.

## 9. Security Review --- User Data Exposure

### Problem identified

Some deal queries initially used broad owner relation inclusion.

### Risk

The User model contains `passwordHash`, so returning the entire owner
object could expose sensitive data to the client.

### Correction

The owner relation was changed to a restricted selection containing only
fields required by the UI, including:

``` text
id
name
email
role
isActive
```

### Verification

The deal response was checked after the change and no longer exposed
`passwordHash`.

## 10. Collaborator Access Security Review

AI-assisted review identified that collaboration must affect both
visibility and update permissions.

### Required behavior

A sales representative should be able to act on:

-   Deals they own.
-   Deals where they are a collaborator.

A sales representative who is neither should not be able to access
another user's deal.

### Verification performed

The following cases were tested:

1.  Admin added a sales representative as a collaborator.
2.  The collaborator could retrieve the deal.
3.  The collaborator could update the deal.
4.  An unrelated sales representative received an access rejection.
5.  Duplicate collaborator addition was rejected.
6.  Collaborator removal worked.

This verified the important security behavior at the API level.

------------------------------------------------------------------------

## 11. Lifecycle Validation

### AI-assisted design principle

Business rules should be enforced by the backend rather than only by
React controls.

### Reason

A user can bypass a browser UI and call the API directly.

### Result

The backend validates:

-   Allowed stage values.
-   One-stage forward movement.
-   One-stage backward movement.
-   Required backward reason.
-   Closed-stage behavior.
-   Manager-only reopen behavior.

## 13. AI Verification Process

For implementation suggestions, the following verification loop was
used:

``` text
Requirement
    ↓
AI proposal
    ↓
Inspect actual source
    ↓
Apply smallest safe change
    ↓
Run/build/test
    ↓
Inspect API/UI behavior
    ↓
Commit incrementally
```

This approach was especially important for:

-   Authentication
-   Authorization
-   Lifecycle rules
-   Prisma relationships
-   Large JSX changes
-   Collaborator access

## 14. AI Usage Principles

The project followed these practical rules:

-   AI output was not treated as automatically correct.
-   Existing project structure was preserved where possible.
-   Security-sensitive changes were verified through API behavior.
-   Database changes were represented through Prisma migrations.
-   Large feature replacements were avoided.
-   Documentation distinguishes implemented behavior from proposed work.
-   Bugs caused by incorrect suggestions were corrected and recorded.
